Домены из ваших списков работают без настройки DNS. keen-pbr сам читает обычные DNS-ответы (порт 53), которые проходят через роутер, и имена сайтов в начале TLS-, HTTP- и QUIC-соединений (это называется L7: имя сайта берётся из первых пакетов соединения). Подробности в разделе [DNS-перехват](#dns-перехват).

## Нужен ли dnsmasq? {#do-i-need-dnsmasq}

**Для маршрутизации нет.** Перехват работает с любым резолвером: DNS-прокси Keenetic, unbound, dnsmasq или другим. Если провайдер подменяет DNS-ответы, обычно хватает DoH/DoT на роутере (DoH и DoT — зашифрованный DNS).

**Да, если вам нужно одно из двух:**

- разрешать домены некоторых списков через отдельный DNS-сервер. Например, CDN (сеть доставки контента) должна отдавать адреса для региона вашего VPN, или домены резолвятся только внутри VPN;
- задать свои DNS-серверы по умолчанию для всей сети прямо в keen-pbr.

Оба случая работают только через dnsmasq. Если ни один вам не подходит, оставьте переключатель **Управлять конфигурацией dnsmasq** выключенным. Если вы обновились с 3.3.x, переключатель уже включён: выключите его, если dnsmasq вам не нужен (см. [Ломающие изменения в 3.4.0]({{< relref "/docs/changelog#upgrading-from-33x" >}})).

Как установить dnsmasq и как вернуть всё обратно: [Keenetic]({{< relref "/docs/getting-started/installation/keenetic#dnsmasq" >}}), [OpenWrt]({{< relref "/docs/getting-started/installation/openwrt#dnsmasq" >}}), [Debian]({{< relref "/docs/getting-started/installation/debian#dnsmasq" >}}).

## Как проверить, что DNS идёт через роутер

Перехват видит только те DNS-запросы, которые проходят через роутер. Если устройство использует DoH или свой DNS-сервер, часть доменов keen-pbr определит только по L7.

1. Откройте **Общее** > **Обзор системы** и найдите карточку **Перехват DNS**.
2. Нажмите **Проверить снова**. Для другого устройства нажмите **Проверить с другого устройства** и выполните показанную команду `nslookup` на компьютере или телефоне, пока окно открыто.

То же можно проверить вручную на устройстве:

```bash {filename="bash"}
nslookup check.keen-pbr.fyi
```

- Ответ `127.0.0.88`: DNS-запросы устройства идут через роутер, всё работает.
- Другой адрес: устройство обходит роутер или использует зашифрованный DNS. Отключите безопасный DNS (DoH) в браузере и системе.
- Нет ответа: DNS на устройстве не работает.

## Отдельные DNS-серверы для списков (dnsmasq) {#per-list-dns-servers-dnsmasq}

Эта функция нужна, когда CDN должна отдавать адреса для региона вашего VPN или когда разным сервисам нужны разные DNS-серверы.

**Пример**: домены AI-сервисов разрешаются через DNS-сервер за VPN. Тогда CDN отдаёт адреса для страны выхода VPN, и сервис не видит, что вы заходите из другой страны (иначе аккаунт могут заблокировать).

{{% steps %}}

### Включите управление dnsmasq

Откройте **Общее** > **Настройки** > **Управление локальным DNS-сервером** и включите **Управлять конфигурацией dnsmasq**. Страницы **DNS серверы** и **Правила DNS** открываются только после этого.

### Добавьте DNS-сервер

Откройте **DNS** > **DNS серверы** > **Добавить DNS-сервер**. Заполните **Название**, **Тип DNS** и **Адрес**. В поле **Делать запросы через Outbound** выберите outbound (канал, через который пойдёт трафик: VPN-интерфейс, провайдер или блокировка), если сервер доступен только через него, например через VPN.

### Привяжите сервер к спискам

Откройте **DNS** > **Правила DNS** > **Добавить правило DNS**. В поле **Списки доменов** выберите списки, а в поле **DNS-сервер** сервер из предыдущего шага.

### Задайте DNS-серверы по умолчанию (необязательно)

В блоке **Вышестоящие DNS-сервера по умолчанию** нажмите **Добавить DNS-сервер по умолчанию** и выберите серверы для всех остальных доменов. Если блок пуст, dnsmasq использует свои обычные DNS-серверы.

### Примените настройки

Нажмите **Применить** (или **Применить и перезапустить**).

{{% /steps %}}

Те же настройки в `config.json`:

```json { filename="config.json" }
{
  "dns": {
    "resolver_integration": "dnsmasq",
    "servers": [
      {"tag": "vpn_dns", "address": "1.1.1.1", "detour": "vpn"},
      {"tag": "isp_dns", "address": "192.168.1.1"}
    ],
    "rules": [
      {
        "list": ["ai_services"],
        "server": "vpn_dns",
        "allow_domain_rebinding": false
      }
    ],
    "fallback": ["isp_dns"]
  }
}
```

**Несколько DNS-серверов для одного списка.** Добавьте для этого списка по правилу на каждый сервер. dnsmasq опрашивает все серверы, пользуется тем, который ответил первым, и переключается на другой, если тот перестал отвечать.

dnsmasq хранит отдельную запись (около 200 байт) для каждой пары «домен — сервер». Каждый дополнительный сервер добавляет столько же памяти на каждый домен списка: два сервера для списка из 10 000 доменов займут около 4 МБ вместо 2 МБ.

## DNS-серверы

Название (`tag`) должно быть уникальным: строчные латинские буквы, цифры и `_`, начинается с буквы, не длиннее 24 символов.

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `tag` | string | да | Название сервера (**Название**) |
| `type` | string | нет | Тип сервера (**Тип DNS**): `static` (**DNS без шифрования**, по умолчанию) или `keenetic` (**Keenetic DNS**, {{< only keenetic >}}) |
| `address` | string | для `static` | IP-адрес DNS-сервера с опциональным портом, например `"10.8.0.1"`, `"10.8.0.1:5353"`, `"2001:4860:4860::8888"` или `"[2001:4860:4860::8888]:5353"` |
| `detour` | string | нет | Outbound, через который роутер сам отправляет запросы к этому серверу (**Делать запросы через Outbound**) |
| `keenetic_upstreams` | array | нет | DNS-серверы Keenetic, которые использует этот сервер (**Вышестоящие серверы**). Каждый элемент содержит `protocol` (`"DoT"`, `"DoH"` или `"Plain"`) и `target`, как их показывает веб-интерфейс. Не задано: все серверы. Только для `type: "keenetic"`. Если серверов два и больше, нельзя сочетать с `detour`. {{< only keenetic >}} |

`detour` нужен, когда DNS-сервер доступен только через определённое соединение, обычно через тот же VPN. Запросы, которые устройства в сети отправляют напрямую на тот же адрес, `detour` не затрагивает: для них нужно обычное правило маршрутизации.

```json { filename="config.json" }
{
  "dns": {
    "servers": [
      {
        "tag": "vpn_dns",
        "type": "static",
        "address": "10.8.0.1:5353",
        "detour": "vpn"
      },
      {
        "tag": "google_dns",
        "address": "8.8.8.8"
      },
      {
        "tag": "google_dns_v6",
        "address": "[2001:4860:4860::8888]:53"
      },
      {
        "tag": "keenetic_dns",
        "type": "keenetic"
      }
    ]
  }
}
```

### Тип «Keenetic DNS»

{{< only keenetic >}}\
На роутерах Keenetic `type: "keenetic"` берёт DNS-серверы из текущих настроек роутера. Их настраивают в веб-интерфейсе Keenetic: **Сетевые правила** > **Интернет-фильтры** > **Настройка DNS**. Если там заданы DoT или DoH серверы, используются только они.

- Поле `address` для него не задаётся.
- keen-pbr берёт серверы без привязки к домену. Если среди них есть зашифрованные ({{< term "DoH" >}}/DoT), используются все такие серверы. Иначе используются все обычные серверы.

#### Вышестоящие серверы

По умолчанию запросы идут во все серверы, заданные в Keenetic. Чтобы использовать только некоторые, отметьте их в поле **Вышестоящие серверы** (`keenetic_upstreams`). В списке видны серверы, заданные в Keenetic, и их тип: DoH, DoT или обычный. Кнопка **Синхронизировать с Keenetic** перечитывает список сразу. Серверы для отдельных доменов (например, провайдера) показаны отдельно: они заданы в общих настройках DNS Keenetic, и кнопка **Открыть настройки DNS Keenetic** ведёт к ним.

- Отмечен один сервер: все запросы идут в него.
- Отмечено два и больше: запросы распределяются по ним по очереди. Если сервер перестал отвечать, его заменяет следующий, а молчащий на время пропускается.

Серверов с `type: "keenetic"` может быть несколько, например один для DoT-серверов и другой для DoH. Так разные списки доменов можно отправить на разные серверы.

```json { filename="config.json" }
{
  "dns": {
    "servers": [
      {
        "tag": "keenetic_dot",
        "type": "keenetic",
        "keenetic_upstreams": [
          { "protocol": "DoT", "target": "8.8.8.8@dns.google" },
          { "protocol": "DoT", "target": "8.8.4.4@dns.google" }
        ]
      }
    ]
  }
}
```

Если отмеченный сервер убрали в настройках Keenetic, keen-pbr использует остальные. Когда не осталось ни одного, домены, для которых выбран этот сервер, не разрешаются. В обоих случаях на странице состояния появляется проблема «DNS-сервер Keenetic не найден».

Изменения в настройках Keenetic keen-pbr подхватывает сам в течение нескольких минут. Кнопка **Синхронизировать с Keenetic** на странице DNS-серверов и в форме сервера делает это сразу.

## Справочник полей

Секция `dns` в `config.json`:

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `servers` | array | нет | Определения DNS-серверов (см. выше) |
| `resolver_integration` | string | нет | `"none"` (по умолчанию) или `"dnsmasq"`. В веб-интерфейсе: **Управлять конфигурацией dnsmasq**. |
| `dnsmasq_instance` | string | нет | Селектор управляемого экземпляра dnsmasq: `uci:<секция>` (OpenWrt), `entware:default` (Keenetic), `systemd:<юнит>.service` (Debian). В веб-интерфейсе: **Экземпляр dnsmasq**. Пусто: автоматический выбор; нужен только если найдено несколько экземпляров. |
| `rules` | array | нет | Правила, которые привязывают списки к DNS-серверам (работают только при `resolver_integration: "dnsmasq"`) |
| `fallback` | array of string | нет | Теги вышестоящих DNS-серверов для запросов, не совпавших с правилом (работают только при `resolver_integration: "dnsmasq"`). В веб-интерфейсе: **Вышестоящие DNS-сервера по умолчанию**. Если не указано, dnsmasq оставляет свои серверы и дополнительно получает серверы из `dnsmasq-fallback.conf`. |
| `dns_test_server` | object | нет | Игнорируется; используйте `intercept.dns.marker` |

Правило (элемент `rules[]`):

| Поле | Тип | По умолчанию | Описание |
|---|---|---|---|
| `enabled` | bool | true | Включено ли правило |
| `list` | array of string | обязательно | Имена списков, домены которых используют этот DNS-сервер (**Списки доменов**) |
| `server` | string | обязательно | Тег DNS-сервера (**DNS-сервер**) |
| `allow_domain_rebinding` | bool | false | Разрешить приватные IP-адреса (RFC1918, адреса локальной сети) в ответах для этих доменов → `rebind-domain-ok` в dnsmasq (**Разрешить DNS rebind для этих доменов**). Включайте, только если список указывает на внутренние сервисы. |

## DNS-перехват

Перехват включён по умолчанию. Настройки: **Общее** > **Настройки** > **Маршрутизация на основе доменов**. Перехват определяет IP-адреса доменов из ваших списков:

- **DNS**: keen-pbr ненадолго задерживает DNS-ответ, проходящий через роутер, добавляет адреса из него в набор списка и только потом отдаёт ответ клиенту. Так первое же соединение к сайту идёт нужным маршрутом.
- **L7**: keen-pbr читает имя сайта в начале TLS-, HTTP- и QUIC-соединений. Это помогает, когда устройство использует зашифрованный DNS. Первое соединение к сайту при этом обрывается, и браузер или приложение подключается заново, уже нужным маршрутом.

Менять эти настройки нужно, только если значения по умолчанию вам не подходят. Секция `intercept` в `config.json`:

| Поле | Тип | По умолчанию | Описание |
|---|---|---|---|
| `enabled` | boolean | `true` | Включить перехват (**Включить маршрутизацию на основе доменов**) |
| `min_ttl_ms` / `max_ttl_ms` | integer | `300000` / `86400000` | Сколько хранить адрес в динамическом наборе: не меньше и не больше указанного, в миллисекундах (округляется до секунд). Внутри этих границ используется {{< term "TTL" >}} из DNS-ответа (**Минимальный TTL**, **Максимальный TTL**) |
| `dns.enabled` | boolean | `true` | Читать DNS-ответы, UDP и TCP (**Перехватывать ответы DNS-серверов**) |
| `dns.queue_num` | integer | `9053` | Номер очереди {{< term "NFQUEUE" >}}. Меняйте, только если он занят другой программой (**Номер NFQUEUE**) |
| `dns.hold_timeout_ms` | integer | `30` | Сколько ждать записи адресов, прежде чем отдать DNS-ответ клиенту. Если не успели, ответ уходит без ожидания (**Тайм-аут удержания DNS**) |
| `dns.marker` | object | `check.keen-pbr.fyi` / `127.0.0.88` | Проверочный домен: если DNS клиента идёт через роутер, на него придёт ответ `127.0.0.88` (**Домен-маркер**, **IPv4-адрес маркера**) |
| `l7.enabled` | boolean | `true` | Читать имена сайтов в соединениях (**Включить перехват L7**) |
| `l7.nflog_group` | integer | `9054` | Номер группы {{< term "NFLOG" >}}. Меняйте, только если он занят другой программой (**Группа NFLOG**) |
| `l7.tls` / `http` / `quic` | boolean | `true` | Какие протоколы читать (**TLS SNI**, **HTTP Host**, **QUIC**) |

### Требования к ядру

Перехват работает на большинстве роутеров. Минимальные версии ядра Linux:

| Бэкенд firewall | Перехват DNS | Перехват L7 |
|---|---|---|
| iptables | 3.8 | 2.6.39 |
| nftables | 4.1 | 4.5 |

Производители роутеров иногда убирают части ядра, поэтому keen-pbr не полагается на номер версии, а при запуске сервиса проверяет, что всё нужное работает. Если чего-то не хватает, отключается только соответствующая часть перехвата, а остальной keen-pbr продолжает работать. Результат проверки виден на странице состояния в веб-интерфейсе и в `GET /api/health/service` (поле `intercept`). Проверка выполняется один раз при запуске: если вы доустановили модули ядра, перезапустите сервис.

## Если используете dnsmasq: установка и проблемы

### Установка по платформам

keen-pbr не устанавливает dnsmasq; поставьте его сами, если нужна эта функция. Пошаговая установка и откат есть на страницах установки: [Keenetic]({{< relref "/docs/getting-started/installation/keenetic#dnsmasq" >}}), [OpenWrt]({{< relref "/docs/getting-started/installation/openwrt#dnsmasq" >}}), [Debian]({{< relref "/docs/getting-started/installation/debian#dnsmasq" >}}). Что keen-pbr меняет на каждой платформе:

**OpenWrt**: установите `dnsmasq`. keen-pbr добавляет в секцию dnsmasq в `/etc/config/dhcp` три записи `addnmount`, чтобы dnsmasq из своей песочницы мог запустить keen-pbr. Пока управление включено и основные DNS-серверы заданы, keen-pbr убирает из `/etc/config/dhcp` серверы без домена, серверы для отдельных доменов остаются. Когда вы выключите управление или очистите основные серверы, убранные серверы вернутся. Записи `addnmount` исчезнут при удалении пакета.

**Keenetic (Entware)**: установите `dnsmasq-full` (заменяет встроенный ndnproxy как LAN-резолвер).
При первом включении управления keen-pbr добавляет в `/opt/etc/dnsmasq.conf` помеченный блок с одной строкой `conf-script`. Тот же блок добавляет `install-recommended-config`. Если dnsmasq не установлен, страница состояния покажет ошибку.

**Debian**: установите `dnsmasq`. При первом включении управления keen-pbr добавляет в `/etc/dnsmasq.conf` помеченный блок. `install-recommended-config` добавляет такой же блок. Если dnsmasq не установлен, страница состояния покажет ошибку.

На Keenetic и Debian есть команда `install-recommended-config` (см. страницы установки). Она заменяет основной конфиг dnsmasq рекомендуемым, сохраняет прежний файл рядом и перезапускает dnsmasq.

### Выбор экземпляра dnsmasq

На роутере может работать несколько экземпляров dnsmasq (на OpenWrt по одному на каждую секцию `dnsmasq` в `/etc/config/dhcp`). keen-pbr управляет ровно одним из них и опознаёт его по **селектору**, то есть по короткому имени экземпляра:

| Платформа | Селектор | Пример |
|---|---|---|
| OpenWrt | `uci:<секция>` (имя из `uci show dhcp`) | `uci:cfg01411c`, `uci:guest` |
| Keenetic ({{< term "Entware" >}}) | `entware:default` | `entware:default` |
| Debian | `systemd:<юнит>.service` | `systemd:dnsmasq.service` |

Экземпляр выбирается в таком порядке:

1. **Явно**: задан `dns.dnsmasq_instance`. Если такого экземпляра нет, keen-pbr сообщает `DNSMASQ_INSTANCE_NOT_FOUND` и ничего не меняет.
2. **По установленному drop-in**: поле пустое, а {{< term "drop-in" >}} keen-pbr уже стоит ровно в одном экземпляре. Он и продолжает использоваться. Если drop-in найден в нескольких, выбор останавливается с ошибкой `DNSMASQ_INSTANCE_AMBIGUOUS`.
3. **Автоматически**: поле пустое, ничего не установлено, и ровно один включённый экземпляр обслуживает DNS (`port` не равен `0`). Если таких нет, результат `DNSMASQ_NO_DNS_INSTANCE`; если несколько, `DNSMASQ_INSTANCE_AMBIGUOUS`.

Если выбор неоднозначен, keen-pbr ничего не меняет и не трогает уже установленные drop-in. Посмотрите кандидатов командой `keen-pbr resolver dnsmasq detect` и задайте экземпляр в **Общее** > **Настройки** > **Управление локальным DNS-сервером** > **Экземпляр dnsmasq** (или `dns.dnsmasq_instance` в `config.json`). Если drop-in keen-pbr стоит ещё и в невыбранном экземпляре, `detect` и журнал покажут предупреждение. Удалите файл drop-in, который назван в предупреждении, и перезапустите этот экземпляр dnsmasq.

#### Определение DNS-адреса

keen-pbr сам находит адрес, на котором отвечает выбранный dnsmasq: читает конфигурацию, которую dnsmasq действительно загрузил, и проверяет адрес DNS-запросом. Если dnsmasq не обслуживает DNS (`port=0`, нет DNS-сокета или он работает в другом {{< term "network namespace" >}}), keen-pbr сообщит об ошибке, а не подставит `127.0.0.1:53` наугад.

#### Проверки перед каждым перезапуском

Перед перезапуском dnsmasq keen-pbr проверяет новые настройки командой `dnsmasq --test` на вашей текущей конфигурации dnsmasq вместе с {{< term "drop-in" >}} keen-pbr. Ещё один раз он проверяет, что ваша сборка dnsmasq поддерживает `conf-script`.

Если проверка не прошла, **dnsmasq не перезапускается и работает со старыми настройками**. Код ошибки и вывод dnsmasq видны в веб-интерфейсе и в `/api/health/service`; исправьте проблему и примените конфигурацию снова.

Каждая проверка запускает генератор конфигурации, поэтому перед каждым применением в системном журнале появляется лишний блок `generate-resolver-config dnsmasq: pid ..., parent ... (dnsmasq)`. Так и должно быть.

#### Ошибки

Код виден в `GET /api/health/service` (`error_code`) и в веб-интерфейсе. Во всех случаях ниже keen-pbr не перезапускает dnsmasq, если в таблице не сказано иное.

| Код | Значение | Что делать |
|---|---|---|
| `DNSMASQ_NO_HOOK` | В этой сборке нет hook-скрипта для dnsmasq. | Используйте пакет, собранный для вашей платформы. |
| `DNSMASQ_HOOK_FAILED` | Вызов `inspect` у hook-скрипта завершился ошибкой или вывел нечитаемый ответ. | Запустите `keen-pbr resolver dnsmasq detect`; проверьте, что hook-скрипт и keen-pbr одной версии. |
| `DNSMASQ_NOT_INSTALLED` | dnsmasq не установлен. | Установите dnsmasq (см. выше) или, если он не нужен, выключите **Управлять конфигурацией dnsmasq** (`dns.resolver_integration: "none"`). |
| `DNSMASQ_NO_DNS_INSTANCE` | Нет включённого экземпляра с DNS. | Включите экземпляр с DNS или выключите **Управлять конфигурацией dnsmasq** (`dns.resolver_integration: "none"`). |
| `DNSMASQ_INSTANCE_NOT_FOUND` | `dns.dnsmasq_instance` указывает на несуществующий экземпляр. | Исправьте селектор; допустимые покажет `keen-pbr resolver dnsmasq detect`. |
| `DNSMASQ_INSTANCE_AMBIGUOUS` | Подходит несколько экземпляров. | Задайте **Экземпляр dnsmasq** (`dns.dnsmasq_instance`). |
| `DNSMASQ_NOT_RUNNING` | Выбранный экземпляр не запущен. | Запустите dnsmasq сами. keen-pbr его не запускает и применит конфигурацию, как только dnsmasq снова заработает. |
| `DNSMASQ_DNS_DISABLED` | У выбранного экземпляра `port=0`. | Выберите другой экземпляр или включите в этом DNS. |
| `DNSMASQ_OTHER_NETNS` | dnsmasq работает в другом сетевом пространстве имён. | Не поддерживается; запустите dnsmasq в основном пространстве роутера. |
| `DNSMASQ_NO_DNS_LISTENER` | Процесс запущен, но у него нет DNS-сокета. | Проверьте `listen-address`, `interface` и `port` в конфигурации dnsmasq. |
| `DNSMASQ_ENDPOINT_UNRESPONSIVE` | Сокеты есть, но ни один не ответил на DNS-запрос. | Проверьте, что dnsmasq работает (`nslookup example.com 127.0.0.1`). Не перезапускается. |
| `DNSMASQ_DROPIN_NOT_LOADED` | Работающий dnsmasq не читает каталог, куда ставится {{< term "drop-in" >}} keen-pbr (или фильтр `conf-dir` отбрасывает имя файла). | Добавьте каталог в `conf-dir` этого экземпляра или ослабьте фильтр. |
| `DNSMASQ_FOREIGN_DROPIN` | Файл drop-in существует, но его создал не keen-pbr. | Переместите или удалите файл; keen-pbr его никогда не перезаписывает. |
| `DNSMASQ_CONF_SCRIPT_UNSUPPORTED` | Эта сборка dnsmasq не выполняет `conf-script`. | Установите сборку dnsmasq с поддержкой `conf-script` (на Keenetic это `dnsmasq-full`). |
| `DNSMASQ_TEST_FAILED` | Даже минимальная конфигурация не проходит `dnsmasq --test`. | Запустите `dnsmasq --test` вручную и исправьте то, что он покажет. |
| `DNSMASQ_PREFLIGHT_FAILED` | Текущая конфигурация dnsmasq вместе с drop-in keen-pbr не проходит `--test`. | Прочитайте вывод dnsmasq в описании ошибки и исправьте конфигурацию. dnsmasq не затронут. |
| `DNSMASQ_APPLY_FAILED` | Hook-скрипт не смог установить drop-in. | Смотрите вывод hook-скрипта в описании ошибки и системный журнал. |
| `DNSMASQ_CONFIG_NOT_LOADED` | dnsmasq перезапущен, но новая конфигурация не появилась вовремя. | Проверьте журнал dnsmasq и примените конфигурацию ещё раз. |
| `DNSMASQ_STAMP_MISMATCH` | dnsmasq работает с другой конфигурацией, чем ожидалось (например, его перезапустил кто-то другой). | keen-pbr чинит это сам в пределах, описанных ниже. |
| `DNSMASQ_REPAIR_PAUSED` | Лимит автоматических исправлений исчерпан. | Выясните, почему dnsmasq теряет конфигурацию, затем примените конфигурацию или перезапустите keen-pbr. |
| `DNSMASQ_PROBE_FAILED` | Процесс жив, но перестал отвечать. | Проверьте dnsmasq. Он не перезапускается. |

### Как это работает

В конфигурации dnsmasq стоит одна строка {{< term "drop-in" >}}: при каждом старте dnsmasq запускает keen-pbr и получает от него правила для списков и основные DNS-серверы.

- Когда **Управлять конфигурацией dnsmasq** включено, dnsmasq перезапускается при изменении этих данных (обновление списка, смена настроек или один раз после старта keen-pbr) и только после проверок из раздела [Проверки перед каждым перезапуском](#проверки-перед-каждым-перезапуском).
- Когда выключено, dnsmasq получает серверы из файла `dnsmasq-fallback.conf` (Keenetic: `/opt/etc/keen-pbr/`, Debian и OpenWrt: `/etc/keen-pbr/`). Они добавляются к собственным серверам dnsmasq. Чтобы этого не было, очистите файл. На OpenWrt он по умолчанию пустой.
- Когда включено, но основные DNS-серверы не заданы, dnsmasq тоже получает серверы из `dnsmasq-fallback.conf`.

### При остановке, отключении или удалении

- **Остановка keen-pbr**: dnsmasq не перезапускается. Отдельные DNS-серверы для списков продолжают работать, в том числе после перезапуска dnsmasq или роутера.
- **Отключение функции** (`resolver_integration: "none"`): keen-pbr перезапускает dnsmasq, и тот переходит на серверы из `dnsmasq-fallback.conf`. На OpenWrt список серверов возвращается в `/etc/config/dhcp`. Если вы выключили управление, правя конфиг при остановленном keen-pbr, первый старт один раз перезапустит dnsmasq. Проверить результат можно командой [`resolver dnsmasq detect`]({{< relref "/docs/cli#resolver-dnsmasq-detect" >}}).
- **dnsmasq не запущен**: keen-pbr никогда не запускает остановленный dnsmasq. Если dnsmasq упал в системе без супервизора служб ({{< term "Entware" >}}), запустите его вручную; keen-pbr применит свою конфигурацию заново, как только dnsmasq снова заработает.
- **dnsmasq потерял конфигурацию** (перезапущен с другими настройками): keen-pbr перезапускает его не более 3 раз (сразу, затем через 5 и 10 минут), после чего автоматическое восстановление приостанавливается; `state` в `/api/health/service` показывает `reconciling` или `error` с причиной. Применение конфигурации или перезапуск keen-pbr включают его снова. Работающий dnsmasq, который не отвечает на проверку конфигурации, не перезапускается.
- **Удаление пакета**: keen-pbr убирает свою запись из dnsmasq, возвращает список серверов на OpenWrt и перезапускает dnsmasq. Это работает, даже если сам keen-pbr сломан: скрипты удаления его не запускают. Если у dnsmasq не остаётся ни одного вышестоящего DNS-сервера (в конфиге `no-resolv` и нет своих строк `server=`), серверы из `dnsmasq-fallback.conf` остаются в блоке с пометкой `keen-pbr fallback upstream` в `/opt/etc/dnsmasq.conf` (Keenetic) или `/etc/dnsmasq.conf` (Debian). Замените их своими. Правила файрвола, оставшиеся после аварийно завершившегося keen-pbr, тоже удаляются.
