Маршрутизация по доменам работает и без настроек DNS: keen-pbr сам читает DNS-ответы и TLS/HTTP/QUIC-трафик и заполняет наборы ваших списков (см. [DNS-перехват](#dns-перехват)). Резолвер для этого настраивать не нужно: dnsmasq, DNS-прокси Keenetic, unbound и любой другой работают так, как вы их настроили.

## Нужен ли dnsmasq? {#do-i-need-dnsmasq}

**Для маршрутизации нет.** Перехват работает с любым резолвером: DNS-прокси Keenetic, unbound, dnsmasq или другим. Если провайдер подменяет DNS-ответы, обычно хватает DoH/DoT на роутере.

**Да, если вам нужны:**

- отдельные DNS-серверы для доменов некоторых списков, например CDN, который должен отвечать для региона вашего VPN, или домены, которые резолвятся только внутри VPN;
- свои DNS-серверы по умолчанию (`fallback`), которыми управляет keen-pbr.

И то и другое работает только через dnsmasq. Установка и откат по платформам: [Keenetic]({{< relref "/docs/getting-started/installation/keenetic#dnsmasq" >}}), [OpenWrt]({{< relref "/docs/getting-started/installation/openwrt#dnsmasq" >}}), [Debian]({{< relref "/docs/getting-started/installation/debian#dnsmasq" >}}). В веб-интерфейсе переключатель называется **Общее** > **Управление локальным DNS-сервером** > **Управлять конфигурацией dnsmasq**.

Настройки на этой странице нужны в двух случаях:

- задать DNS-серверы и указать, через какой outbound к ним обращаться (`detour`);
- разрешать домены из выбранных списков через отдельный DNS-сервер, обычно доступный через тот же VPN. Только для этого keen-pbr управляет dnsmasq, и только если вы это включили.

## Конфигурация

```json { filename="config.json" }
{
  "dns": {
    "servers": [...]
  }
}
```

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `servers` | array | нет | Определения DNS-серверов |
| `resolver_integration` | string | нет | `"none"` (по умолчанию) или `"dnsmasq"`. В веб-интерфейсе: **Управлять конфигурацией dnsmasq**. Конфиги от 3.3.x (без поля `version`) остаются на `"dnsmasq"`. |
| `dnsmasq_instance` | string | нет | Селектор управляемого экземпляра dnsmasq: `uci:<секция>` (OpenWrt), `entware:default` (Keenetic), `systemd:<юнит>.service` (Debian). Пусто или не задано: автоматический выбор; нужен только если найдено несколько экземпляров. |
| `rules` | array | нет | Правила маршрутизации списков на DNS-серверы (активны только при `resolver_integration: "dnsmasq"`). |
| `fallback` | array of string | нет | Теги upstream DNS-серверов для запросов, не совпавших с правилом (активны только при `resolver_integration: "dnsmasq"`). |
| `dns_test_server` | object | нет | Устаревшее поле, принимается, но игнорируется; используйте `intercept.dns.marker` |

## Отдельные DNS-серверы для списков (dnsmasq) {#per-list-dns-servers-dnsmasq}

Когда `resolver_integration` равен `"dnsmasq"`, keen-pbr настраивает dnsmasq так, чтобы домены из выбранных списков разрешались через указанные DNS-серверы. Это нужно, когда CDN должна отдавать адреса для региона вашего VPN или когда разным сервисам нужны разные DNS-серверы.

**Пример**: домены AI-сервисов разрешаются через DNS-сервер за VPN. Тогда CDN отдаёт адреса для страны выхода VPN, и сервис не видит, что вы заходите из другой страны (иначе аккаунт могут заблокировать).

### Пример конфигурации

```json { filename="config.json" }
{
  "dns": {
    "resolver_integration": "dnsmasq",
    "servers": [
      {"tag": "vpn_dns", "address": "1.1.1.1", "detour": "vpn"},
      {"tag": "isp_dns", "address": "192.168.1.1"}
    ],
    "rules": [
      {
        "list": ["ai_services"],
        "server": "vpn_dns",
        "allow_domain_rebinding": false
      }
    ],
    "fallback": ["isp_dns"]
  }
}
```

### Справочник полей

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `resolver_integration` | string | да | Установите `"dnsmasq"` для включения интеграции |
| `servers` | array | да | Определения DNS-серверов (каждый имеет `tag`, опциональные `address` и `detour`) |
| `rules` | array | нет | Массив правил маршрутизации; каждое правило связывает списки с DNS-сервером |
| `fallback` | array | нет | Теги серверов для использования, когда никакое правило не совпадает; если не указано, используются upstream-серверы из resolv.conf |

**DNS-правило** (элемент `rules[]`):

| Поле | Тип | По умолчанию | Описание |
|---|---|---|---|
| `enabled` | bool | true | Включено ли это правило |
| `list` | array of string | обязательно | Имена списков, домены которых должны использовать этот DNS-сервер |
| `server` | string | обязательно | Тег DNS-сервера для доменов в этих списках |
| `allow_domain_rebinding` | bool | false | Разрешить приватные IP-адреса (RFC1918) в ответах → `rebind-domain-ok` в dnsmasq |

**Несколько DNS-серверов для одного списка.** Добавьте для этого списка по правилу на каждый сервер. Домены списка получат серверы всех включённых правил в порядке правил. dnsmasq опрашивает их все, затем пользуется тем, который ответил первым, и переключается на другой, если тот перестал отвечать. Rebinding разрешён, если его разрешает хотя бы одно из этих правил.

dnsmasq хранит отдельную запись (около 200 байт) для каждой пары «домен — сервер». Каждый дополнительный сервер добавляет столько же памяти на каждый домен списка: два сервера для списка из 10 000 доменов займут около 4 МБ вместо 2 МБ.

### Установка по платформам

keen-pbr не устанавливает dnsmasq; поставьте его сами, если нужна эта функция. Пошаговая установка и откат есть на страницах установки: [Keenetic]({{< relref "/docs/getting-started/installation/keenetic#dnsmasq" >}}), [OpenWrt]({{< relref "/docs/getting-started/installation/openwrt#dnsmasq" >}}), [Debian]({{< relref "/docs/getting-started/installation/debian#dnsmasq" >}}). Что keen-pbr меняет на каждой платформе:

**OpenWrt**: установите `dnsmasq`. keen-pbr добавляет в секцию dnsmasq в `/etc/config/dhcp` записи `addnmount`, чтобы dnsmasq из своей песочницы мог запустить keen-pbr. При отключении функции keen-pbr удаляет только те записи, которые добавил сам.

**Keenetic (Entware)**: установите `dnsmasq-full` (заменяет встроенный ndnproxy как LAN-резолвер).
keen-pbr добавляет в `/opt/etc/dnsmasq.conf` помеченный блок со строкой `conf-dir=/tmp/keen-pbr/dnsmasq.d,*.conf`, а скрипт `S55keen-pbr-dnsmasq` при загрузке роутера заново создаёт файл в этом каталоге. Если dnsmasq не установлен, страница состояния покажет ошибку.

**Debian**: установите `dnsmasq`. keen-pbr создаёт файл `/etc/dnsmasq.d/keen-pbr-upstream-dns.conf` из одной строки `conf-script`.

### Выбор экземпляра dnsmasq

На роутере может работать несколько экземпляров dnsmasq (на OpenWrt по одному на каждую секцию `dnsmasq` в `/etc/config/dhcp`). keen-pbr управляет ровно одним из них и опознаёт его по **селектору**:

| Платформа | Селектор | Пример |
|---|---|---|
| OpenWrt | `uci:<секция>` (имя из `uci show dhcp`) | `uci:cfg01411c`, `uci:guest` |
| Keenetic ({{< term "Entware" >}}) | `entware:default` | `entware:default` |
| Debian | `systemd:<юнит>.service` | `systemd:dnsmasq.service` |

Экземпляр выбирается в таком порядке:

1. **Явно**: задан `dns.dnsmasq_instance`. Если такого экземпляра нет, keen-pbr сообщает `DNSMASQ_INSTANCE_NOT_FOUND` и ничего не меняет.
2. **По установленному drop-in**: поле пустое, а {{< term "drop-in" >}} keen-pbr уже стоит ровно в одном экземпляре. Он и продолжает использоваться. Если drop-in найден в нескольких, выбор останавливается с ошибкой `DNSMASQ_INSTANCE_AMBIGUOUS`.
3. **Автоматически**: поле пустое, ничего не установлено, и ровно один включённый экземпляр обслуживает DNS (`port` не равен `0`). Если таких нет, результат `DNSMASQ_NO_DNS_INSTANCE`; если несколько, `DNSMASQ_INSTANCE_AMBIGUOUS`.

Если выбор неоднозначен, keen-pbr не гадает: ничего не меняет и не трогает уже установленные drop-in. Посмотрите кандидатов командой `keen-pbr dnsmasq detect` и задайте `dns.dnsmasq_instance` в `config.json` или в настройках DNS в веб-интерфейсе. Если drop-in keen-pbr стоит ещё и в невыбранном экземпляре, `detect` и журнал покажут предупреждение с командой для его удаления (`keen-pbr dnsmasq remove <селектор>`).

#### Определение DNS-адреса

keen-pbr сам находит адрес, на котором отвечает выбранный dnsmasq: читает конфигурацию, которую dnsmasq действительно загрузил, и проверяет адрес DNS-запросом. Если dnsmasq не обслуживает DNS (`port=0`, нет DNS-сокета или он работает в другом {{< term "network namespace" >}}), keen-pbr сообщит об ошибке, а не подставит `127.0.0.1:53` наугад.

#### Проверки перед каждым перезапуском

Перед перезапуском dnsmasq keen-pbr проверяет новые настройки командой `dnsmasq --test` на вашей текущей конфигурации dnsmasq вместе с {{< term "drop-in" >}} keen-pbr. Ещё один раз он проверяет, что ваша сборка dnsmasq поддерживает `conf-script`.

Если проверка не прошла, **dnsmasq не перезапускается и работает со старыми настройками**. Код ошибки и вывод dnsmasq видны в веб-интерфейсе и в `/api/health/service`; исправьте проблему и примените конфигурацию снова.

Каждая проверка запускает генератор конфигурации, поэтому перед каждым применением в системном журнале появляется лишний блок `generate-resolver-config dnsmasq: pid ..., parent ... (dnsmasq)`. Так и должно быть.

#### Ошибки

Код виден в `GET /api/health/service` (`error_code`) и в веб-интерфейсе. Во всех случаях ниже keen-pbr не перезапускает dnsmasq, если в таблице не сказано иное.

| Код | Значение | Что делать |
|---|---|---|
| `DNSMASQ_NO_HOOK` | В этой сборке нет hook-скрипта для dnsmasq. | Используйте пакет, собранный для вашей платформы. |
| `DNSMASQ_HOOK_FAILED` | Вызов `inspect` у hook-скрипта завершился ошибкой или вывел нечитаемый ответ. | Запустите `keen-pbr dnsmasq detect`; проверьте, что hook-скрипт и keen-pbr одной версии. |
| `DNSMASQ_NOT_INSTALLED` | dnsmasq не установлен. | Установите dnsmasq (см. выше) или, если он не нужен, выключите **Управлять конфигурацией dnsmasq** в веб-интерфейсе (`dns.resolver_integration: "none"`). |
| `DNSMASQ_NO_DNS_INSTANCE` | Нет включённого экземпляра с DNS. | Включите экземпляр с DNS или выключите **Управлять конфигурацией dnsmasq** в веб-интерфейсе (`dns.resolver_integration: "none"`). |
| `DNSMASQ_INSTANCE_NOT_FOUND` | `dns.dnsmasq_instance` указывает на несуществующий экземпляр. | Исправьте селектор; допустимые покажет `keen-pbr dnsmasq detect`. |
| `DNSMASQ_INSTANCE_AMBIGUOUS` | Подходит несколько экземпляров. | Задайте `dns.dnsmasq_instance`. |
| `DNSMASQ_NOT_RUNNING` | Выбранный экземпляр не запущен. | Запустите dnsmasq сами. keen-pbr его не запускает и применит конфигурацию, как только dnsmasq снова заработает. |
| `DNSMASQ_DNS_DISABLED` | У выбранного экземпляра `port=0`. | Выберите другой экземпляр или включите в этом DNS. |
| `DNSMASQ_OTHER_NETNS` | dnsmasq работает в другом сетевом пространстве имён. | Не поддерживается; запустите dnsmasq в основном пространстве роутера. |
| `DNSMASQ_NO_DNS_LISTENER` | Процесс запущен, но у него нет DNS-сокета. | Проверьте `listen-address`, `interface` и `port` в конфигурации dnsmasq. |
| `DNSMASQ_ENDPOINT_UNRESPONSIVE` | Сокеты есть, но ни один не ответил на DNS-запрос. | Проверьте, что dnsmasq работает (`nslookup example.com 127.0.0.1`). Не перезапускается. |
| `DNSMASQ_DROPIN_NOT_LOADED` | Работающий dnsmasq не читает каталог, куда ставится {{< term "drop-in" >}} keen-pbr (или фильтр `conf-dir` отбрасывает имя файла). | Добавьте каталог в `conf-dir` этого экземпляра или ослабьте фильтр. |
| `DNSMASQ_FOREIGN_DROPIN` | Файл drop-in существует, но его создал не keen-pbr. | Переместите или удалите файл; keen-pbr его никогда не перезаписывает. |
| `DNSMASQ_CONF_SCRIPT_UNSUPPORTED` | Эта сборка dnsmasq не выполняет `conf-script`. | Установите сборку dnsmasq с поддержкой `conf-script` (на Keenetic это `dnsmasq-full`). |
| `DNSMASQ_TEST_FAILED` | Даже минимальная конфигурация не проходит `dnsmasq --test`. | Запустите `dnsmasq --test` вручную и исправьте то, что он покажет. |
| `DNSMASQ_PREFLIGHT_FAILED` | Текущая конфигурация dnsmasq вместе с drop-in keen-pbr не проходит `--test`. | Прочитайте вывод dnsmasq в описании ошибки и исправьте конфигурацию. dnsmasq не затронут. |
| `DNSMASQ_APPLY_FAILED` | Hook-скрипт не смог установить drop-in. | Смотрите вывод hook-скрипта в описании ошибки и системный журнал. |
| `DNSMASQ_CONFIG_NOT_LOADED` | dnsmasq перезапущен, но новая конфигурация не появилась вовремя. | Проверьте журнал dnsmasq и примените конфигурацию ещё раз. |
| `DNSMASQ_STAMP_MISMATCH` | dnsmasq работает с другой конфигурацией, чем ожидалось (например, его перезапустил кто-то другой). | keen-pbr чинит это сам в пределах, описанных ниже. |
| `DNSMASQ_REPAIR_PAUSED` | Лимит автоматических исправлений исчерпан. | Выясните, почему dnsmasq теряет конфигурацию, затем примените конфигурацию или перезапустите keen-pbr. |
| `DNSMASQ_PROBE_FAILED` | Процесс жив, но перестал отвечать. | Проверьте dnsmasq. Он не перезапускается. |

### Как это работает

keen-pbr никогда не пишет сгенерированный конфиг dnsmasq на диск. Вместо этого:
1. keen-pbr генерирует конфиг (правила «домен → список», резервные серверы и т.д.)
2. keen-pbr размещает однострочный {{< term "drop-in" >}} (`conf-script=keen-pbr generate-resolver-config dnsmasq`) в каталог в оперативной памяти (tmpfs)
3. dnsmasq запускает эту команду при старте и читает конфиг из её вывода
4. dnsmasq перезапускается только когда генерируемый конфиг меняется (обновление списка, изменение настроек или один раз после старта keen-pbr) и только после проверок из раздела [Проверки перед каждым перезапуском](#проверки-перед-каждым-перезапуском)

### При остановке, отключении или удалении

- **Остановка keen-pbr**: dnsmasq НЕ перезапускается; отдельные DNS-серверы для списков продолжают работать.
- **Отключение функции** (`resolver_integration: "none"`): если выключить её при работающем keen-pbr, {{< term "drop-in" >}} удаляется из выбранного экземпляра, и этот экземпляр перезапускается (возврат к upstream-серверам из resolv.conf). Пока функция выключена, keen-pbr не трогает dnsmasq, в том числе при старте. Поэтому если отключить функцию и потом перезапустить keen-pbr, либо убрать интеграцию из конфига при остановленном keen-pbr, drop-in останется на месте. Он безвреден: при выключенной интеграции выводит только комментарий. Такие остатки показывает `keen-pbr dnsmasq detect`, а удаляет `keen-pbr dnsmasq remove <селектор>`. См. [команды `dnsmasq`]({{< relref "/docs/cli#dnsmasq-detect-and-remove" >}}).
- **dnsmasq не запущен**: keen-pbr никогда не запускает остановленный dnsmasq. Если dnsmasq упал в системе без супервизора служб ({{< term "Entware" >}}), запустите его вручную; keen-pbr применит свою конфигурацию заново, как только dnsmasq снова заработает.
- **dnsmasq потерял конфигурацию** (перезапущен кем-то другим, drop-in исчез): keen-pbr перезапускает его не более 3 раз (сразу, затем через 5 и 10 минут), после чего автоматическое восстановление приостанавливается; `state` в `/api/health/service` показывает `reconciling` или `error` с причиной. Применение конфигурации или перезапуск keen-pbr включают его снова. Работающий dnsmasq, который не отвечает на проверку конфигурации, не перезапускается.
- **Удаление пакета**: drop-in и любые постоянные изменения в конфиге dnsmasq удаляются у всех экземпляров, dnsmasq перезапускается. Это работает, даже если сам keen-pbr сломан или неправильно настроен: скрипты удаления его не запускают. В {{< term "Entware" >}}, если у dnsmasq не остаётся ни одного вышестоящего DNS-сервера, серверы из `dnsmasq-fallback.conf` добавляются в `/opt/etc/dnsmasq.conf` в блок с пометкой `keen-pbr fallback upstream`. Правила файрвола, оставшиеся после аварийно завершившегося keen-pbr, тоже удаляются.

### Решение проблем

См. [Не работают отдельные DNS-серверы для списков]({{< relref "/docs/troubleshooting#per-list-dns-servers-do-not-work" >}}).

## DNS-перехват

Секция `intercept` включена по умолчанию. Она отвечает за то, как keen-pbr узнаёт IP-адреса доменов из ваших списков:

- **DNS** — keen-pbr ненадолго задерживает DNS-ответ, проходящий через роутер, добавляет адреса из него в набор списка и только потом отдаёт ответ клиенту. Так первое же соединение к сайту идёт нужным маршрутом.
- **L7** — keen-pbr читает имя сайта в начале TLS-, HTTP- и QUIC-соединений. Это помогает, когда устройство использует зашифрованный DNS.

Менять эти настройки нужно, только если значения по умолчанию вам не подходят:

| Поле | Тип | По умолчанию | Описание |
|---|---|---|---|
| `enabled` | boolean | `true` | Включить перехват |
| `min_ttl_ms` / `max_ttl_ms` | integer | `300000` / `86400000` | Сколько хранить адрес в динамическом наборе: не меньше и не больше указанного, в миллисекундах (округляется до секунд). Внутри этих границ используется {{< term "TTL" >}} из DNS-ответа |
| `dns.enabled` | boolean | `true` | Читать DNS-ответы (UDP и TCP) |
| `dns.queue_num` | integer | `9053` | Номер очереди {{< term "NFQUEUE" >}}. Меняйте, только если он занят другой программой |
| `dns.hold_timeout_ms` | integer | `30` | Сколько ждать записи адресов, прежде чем отдать DNS-ответ клиенту. Если не успели, ответ уходит без ожидания |
| `dns.marker` | object | `check.keen-pbr.fyi` / `127.0.0.88` | Проверочный домен: если DNS клиента идёт через роутер, на него придёт ответ `127.0.0.88` |
| `l7.enabled` | boolean | `true` | Читать имена сайтов в соединениях |
| `l7.nflog_group` | integer | `9054` | Номер группы {{< term "NFLOG" >}}. Меняйте, только если он занят другой программой |
| `l7.tls` / `http` / `quic` | boolean | `true` | Какие протоколы читать |

Поле `dns.dns_test_server` из прошлых версий больше ни на что не влияет. Для проверки DNS используйте `nslookup check.keen-pbr.fyi` или виджет проверки DNS в веб-интерфейсе.

### Требования к ядру

Перехват работает на большинстве роутеров. Минимальные версии ядра Linux:

| Бэкенд firewall | Перехват DNS | Перехват L7 |
|---|---|---|
| iptables | 3.8 | 2.6.39 |
| nftables | 4.1 | 4.5 |

Производители роутеров иногда убирают части ядра, поэтому keen-pbr не полагается на номер версии, а при запуске сервиса проверяет, что всё нужное работает. Если чего-то не хватает, отключается только соответствующая часть перехвата, а остальной keen-pbr продолжает работать. Результат проверки виден на странице состояния в веб-интерфейсе и в `GET /api/health/service` (поле `intercept`). Проверка выполняется один раз при запуске: если вы доустановили модули ядра, перезапустите сервис.

## DNS-серверы

`tag` сервера должен быть уникальным и подчиняется тем же правилам, что и теги outbound: строчные латинские буквы, цифры и `_`, начинается с буквы, не длиннее 24 символов.

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `tag` | string | да | Уникальный идентификатор для этого DNS-сервера |
| `type` | string | нет | Тип источника DNS: `static` (по умолчанию) или `keenetic` |
| `address` | string | для `static` | IP-адрес DNS-сервера с опциональным портом, например `"10.8.0.1"`, `"10.8.0.1:5353"`, `"2001:4860:4860::8888"` или `"[2001:4860:4860::8888]:5353"` |
| `detour` | string | нет | Outbound для использования при обращении к этому DNS-серверу |

`detour` нужен, когда DNS-сервер доступен только через определённое соединение, обычно через тот же VPN.

```json { filename="config.json" }
{
  "dns": {
    "servers": [
      {
        "tag": "vpn_dns",
        "type": "static",
        "address": "10.8.0.1:5353",
        "detour": "vpn"
      },
      {
        "tag": "google_dns",
        "address": "8.8.8.8"
      },
      {
        "tag": "google_dns_v6",
        "address": "[2001:4860:4860::8888]:53"
      },
      {
        "tag": "keenetic_dns",
        "type": "keenetic"
      }
    ]
  }
}
```

### `type: keenetic` (встроенный DNS роутера через RCI)

На роутерах Keenetic `type: "keenetic"` берёт DNS-серверы из текущих настроек роутера.

Правила и поведение:

- Разрешён максимум один элемент в `dns.servers` с `type: "keenetic"`.
- Для `type: "keenetic"` поле `address` не должно быть задано (адреса берутся из {{< term "RCI" >}}).
- keen-pbr читает строки `dns_server = ...` без привязки к домену из политики прокси **System**.
- Если среди них есть зашифрованные серверы ({{< term "DoH" >}}/DoT), используются все такие серверы по порядку.
- Иначе по порядку используются все обычные (незашифрованные) серверы.

### Как работает `detour`

С `detour` DNS-запросы, которые сам роутер отправляет на этот сервер (например, от dnsmasq), идут через указанный outbound. Например, если у `vpn_dns` задан `detour: "vpn"`, роутер обращается к `vpn_dns` через `vpn`.

Запросы, которые устройства в сети отправляют напрямую на тот же адрес, это не затрагивает: для них нужно обычное правило маршрутизации.
