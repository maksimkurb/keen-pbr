Большинству пользователей эта страница не понадобится.

Здесь описаны настройки для продвинутых сценариев и на уровне сервиса: `daemon`, `api`, `fwmark`, `iproute` и `lists_autoupdate`.

## daemon

Управляет путём к PID-файлу, каталогом кэша и глобальным поведением маршрутизации.

| Поле | Тип | По умолчанию | Описание |
|---|---|---|---|
| `pid_file` | string | — | Путь к PID-файлу |
| `cache_dir` | string | `/var/cache/keen-pbr` | Каталог для кэшированных данных списков |
| `firewall_backend` | string | `"auto"` | Бэкенд firewall: `auto`, `iptables` или `nftables` |
| `clear_dynamic_sets_on_apply` | boolean | `false` | Очищать динамические наборы (IP-адреса доменов, собранные из DNS-ответов и соединений) при каждом применении конфигурации или перезапуске сервиса. При обновлении списков и переключении каналов они не очищаются. |
| `ipset_hashsize` | integer | отсутствует | Необязательный начальный размер хеш-таблицы {{< term "ipset" >}}, создаваемых бэкендом iptables (по умолчанию `1024`). Не действует с nftables. Допустимый диапазон: от 1 до 2147483648. При изменении наборы пересоздаются, а динамические наборы очищаются. |
| `ipset_maxelem` | integer | отсутствует | Необязательное максимальное число элементов ipset, создаваемых бэкендом iptables (по умолчанию `65536`). Не действует с nftables. Допустимый диапазон: от 1 до 4294967295. При изменении наборы пересоздаются, а динамические наборы очищаются. |
| `reuse_static_sets_on_runtime_refresh` | boolean | `true` | Не перезаполнять наборы списков при `SIGUSR1`, переключении `urltest`/`icmptest` и изменении состояния интерфейсов: обновляются только правила, это быстрее. При `false` наборы перезаполняются каждый раз. |
| `strict_enforcement` | boolean | `false` | Если интерфейс или шлюз outbound типа `interface` недоступен, не выпускать его трафик через обычное соединение: в таблицу outbound ставится маршрут из `strict_enforcement_action`. Можно задать для каждого outbound отдельно. |
| `strict_enforcement_action` | string | `"unreachable"` | Что делать с трафиком при `strict_enforcement`: `unreachable` сразу возвращает приложению сетевую ошибку, а `blackhole` молча отбрасывает пакеты до тайм-аута приложения. |
| `max_file_size_bytes` | integer | `8388608` (8 MiB) | Максимальный размер загруженного удалённого списка в байтах |
| `firewall_verify_max_bytes` | integer | `262144` | Сколько байт вывода `iptables`/`nft` читать при проверке правил firewall (`keen-pbr status`, страница состояния); `0` — без ограничения |

```json { filename="config.json" }
{
  "daemon": {
    "pid_file": "/var/run/keen-pbr.pid",
    "cache_dir": "/var/cache/keen-pbr",
    "firewall_backend": "auto",
    "clear_dynamic_sets_on_apply": false,
    "ipset_hashsize": null,
    "ipset_maxelem": null,
    "reuse_static_sets_on_runtime_refresh": true,
    "strict_enforcement": false,
    "strict_enforcement_action": "unreachable",
    "max_file_size_bytes": 8388608,
    "firewall_verify_max_bytes": 262144
  }
}
```

Каталог кэша хранит загруженные удалённые списки, чтобы они были доступны, если сеть недоступна при запуске.

## api

Управляет встроенным HTTP API-сервером.

| Поле | Тип | По умолчанию | Описание |
|---|---|---|---|
| `enabled` | boolean | `false` | Включить HTTP API |
| `listen` | string | `"0.0.0.0:12121"` | Адрес и порт для прослушивания |

```json { filename="config.json" }
{
  "api": {
    "enabled": true,
    "listen": "0.0.0.0:12121"
  }
}
```

API также может быть отключён во время выполнения с помощью `--no-api`, независимо от настройки в конфиге. См. [REST API]({{< relref "/docs/rest-api" >}}) для документации эндпоинтов и управлений во время выполнения.

## fwmark

Задаёт диапазон значений {{< term "fwmark" >}}, которые keen-pbr ставит пакетам, чтобы направить их в нужную таблицу маршрутизации. См. [fwmark и conntrack]({{< relref "/docs/concepts#fwmark-и-conntrack" >}}).

| Поле | Тип | По умолчанию | Описание |
|---|---|---|---|
| `start` | string | `"0x00010000"` | Первое значение fwmark для назначения outbounds |
| `mask` | string | `"0x00FF0000"` | Битовая маска fwmark |

```json { filename="config.json" }
{
  "fwmark": {
    "start": "0x00010000",
    "mask": "0x00FF0000"
  }
}
```

`mask` должна состоять из идущих подряд шестнадцатеричных цифр `F`, например `0x00FF0000`. Outbounds получают значения fwmark по порядку, начиная со `start`, в пределах `mask`.

{{< callout type="warning" >}}
Если другое программное обеспечение на вашей системе использует тот же диапазон fwmark, скорректируйте `start` и `mask`, чтобы избежать конфликтов.
{{< /callout >}}

## iproute

Задаёт номера таблиц маршрутизации и приоритеты `ip rule`, которые keen-pbr создаёт для outbounds.

| Поле | Тип | По умолчанию | Описание |
|---|---|---|---|
| `table_start` | integer | `150` | Первый ID таблицы маршрутизации для выделения под outbounds |
| `rule_priority_start` | integer или null | `table_start` | Приоритет первой записи `ip rule`; `null` — такой же, как `table_start` |
| `process_router_traffic` | boolean | `false` | Применять правила маршрутизации к трафику самого роутера и собирать по нему IP-адреса доменов. При `false` keen-pbr обрабатывает только трафик устройств в сети. `detour` у DNS-серверов работает в любом случае. |

```json { filename="config.json" }
{
  "iproute": {
    "table_start": 150,
    "rule_priority_start": null,
    "process_router_traffic": false
  }
}
```

Outbounds получают последовательные ID таблиц, начиная с `table_start`. Убедитесь, что эти ID не конфликтуют с существующими таблицами маршрутизации в вашей системе.

keen-pbr удаляет из таблицы только те маршруты, которые добавил сам. Маршруты, добавленные вами или другими программами, остаются на месте при перезагрузке и остановке keen-pbr.

## Резервный канал (failover)

Правила проверяются сверху вниз, и срабатывает первое подходящее. Поэтому два одинаковых правила с разными outbound не дают резервирования: до второго правила пакет никогда не дойдёт.

Если интерфейс первого outbound пропадёт, поведение зависит от `strict_enforcement`:

- выключен (по умолчанию) — трафик уйдёт через обычный шлюз провайдера, мимо VPN;
- включён — трафик будет заблокирован (как именно, задаёт `strict_enforcement_action`).

Чтобы трафик переключался на запасной канал, создайте один outbound типа `urltest` и добавьте в него оба интерфейса. Параметр `conntrack_on_switch` определяет, что происходит с уже открытыми соединениями, когда `urltest` переходит на более быстрый канал: `preserve` (по умолчанию) оставляет их на старом канале, `delete` удаляет их записи из {{< term "conntrack" >}}, и приложения переподключаются через новый. Если выбранный канал перестал работать, записи conntrack его соединений удаляются всегда.

## Что keen-pbr не делает

- `ipv6_enabled: false` не блокирует IPv6. keen-pbr просто перестаёт маршрутизировать IPv6-трафик, и он идёт как обычно.
- keen-pbr узнаёт IP-адреса доменов из обычных DNS-ответов, которые проходят через роутер, даже если клиент пользуется сторонним DNS-сервером. Зашифрованный DNS ({{< term "DoH" >}}, {{< term "DoT" >}}) прочитать нельзя. Если устройство использует его, keen-pbr узнает адрес сайта только из самого соединения (имя сервера в TLS, HTTP или {{< term "QUIC" >}}), и первые соединения могут пройти мимо VPN. Чтобы этого избежать, отключите на устройстве «безопасный DNS» и настройте DoH/DoT на самом роутере.
- Когда у адреса домена истекает срок в списке, это влияет только на новые соединения. Уже открытые соединения продолжают идти прежним маршрутом: их {{< term "fwmark" >}} хранится в {{< term "conntrack" >}}.
- `keen-pbr download` только скачивает списки в кэш. Чтобы работающий сервис начал их использовать, выполните `keen-pbr download --reload` или перезапустите сервис.
- Не меняйте `fwmark.mask`, пока keen-pbr остановлен после сбоя. Иначе при следующем запуске он не узнает свои старые правила и не сможет их удалить. Если так уже случилось, перезагрузите роутер.

## Только один экземпляр

На одном роутере может работать только один keen-pbr. Отдельный `pid_file` не помогает: второй экземпляр использует те же имена правил и наборов firewall и сломает правила первого.

Все outbound и правила маршрутизации описывайте в одной конфигурации. Если вам действительно нужны два независимых экземпляра, запускайте их в разных сетевых пространствах имён ({{< term "network namespace" >}}).

## lists_autoupdate

Управляет автоматическим периодическим обновлением удалённых списков.

Если секция `lists_autoupdate` не указана, автоматическое обновление выключено.

| Поле | Тип | По умолчанию | Описание |
|---|---|---|---|
| `enabled` | boolean | `false` | Включить автоматическое обновление списков |
| `cron` | string | — | Стандартное 5-полевное выражение cron для расписания обновления |

```json { filename="config.json" }
{
  "lists_autoupdate": {
    "enabled": true,
    "cron": "0 4 * * 0"
  }
}
```

Поле `cron` использует стандартный 5-полевой формат: `минута час день-месяца месяц день-недели`. Пример выше запускается раз в неделю в воскресенье в 04:00.

Поле `cron` валидируется, даже когда `enabled` установлен в `false`.

Если удалённый список не удалось скачать при старте, демон повторяет попытки в фоне с увеличивающимися паузами (10 секунд, 30 секунд, 2 минуты, затем каждые 5 минут), пока загрузка не удастся. Это не зависит от `lists_autoupdate`. Первая загрузка списка, которого ещё нет в кэше, происходит до того, как keen-pbr применит новые настройки dnsmasq, поэтому отдельные DNS-серверы для списков к ней могут не примениться. Повторные попытки их уже используют.

Вы также можете запустить обновление вручную в любое время:
- Отправьте `SIGHUP` в процесс демона: `kill -HUP $(cat /var/run/keen-pbr.pid)`
