title: Outbounds

---

Outbounds сообщают keen-pbr, куда отправить совпавший трафик.

`tag` outbound: строчные латинские буквы, цифры и `_`, начинается с буквы, не длиннее 24 символов (`^[a-z][a-z0-9_]*$`).

Большинству пользователей достаточно:

- одного outbound типа `interface` для VPN-соединения
- одного outbound типа `table` с `table: 254` (основная таблица маршрутизации системы) для обычного соединения, как правило `wan`
- при необходимости — одного outbound типа `urltest` для автоматического выбора лучшего из нескольких соединений

Если не знаете, с чего начать, возьмите тип `interface` и вернитесь к остальным позже.

## Общий пример

```json { filename="config.json" }
{
  "outbounds": [
    {
      "type": "interface",
      "tag": "vpn",
      "interface": "tun0",
      "gateway": "10.8.0.1",
      "gateway6": "2001:db8::1"
    },
    {
      "type": "table",
      "tag": "wan",
      "table": 254
    }
  ]
}
```

## Типы

## `interface`

Используйте, когда хотите отправить трафик через конкретное соединение, например VPN-туннель или обычное интернет-соединение.

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `tag` | string | да | Уникальный идентификатор |
| `type` | string | да | `"interface"` |
| `interface` | string | да | Имя исходящего сетевого интерфейса (напр. `tun0`) |
| `gateway` | string | нет | Необязательный IPv4-адрес шлюза |
| `gateway6` | string | нет | Необязательный IPv6-адрес шлюза |

Для туннелей вроде `tun0` или `wg0` шлюз обычно не нужен: без `gateway` и `gateway6` трафик IPv4 и IPv6 отправляется прямо в интерфейс. Шлюз задают, когда следующий узел нужно указать явно, например для второго WAN за роутером провайдера.

Если задать только один из них, трафик другой версии IP для этого outbound блокируется, а не уходит мимо VPN.

```json { filename="config.json" }
{
  "outbounds": [
    {
      "type": "interface",
      "tag": "vpn",
      "interface": "tun0",
      "gateway": "10.8.0.1",
      "gateway6": "2001:db8::1"
    }
  ]
}
```

## `table`

Отправляет трафик через существующую таблицу маршрутизации: обычно `254`, основную таблицу системы (обычное интернет-соединение), или таблицу, которую создал другой сервис.

Посмотреть, какие таблицы есть и как они называются:

```bash {filename="bash"}
ip rule show
cat /etc/iproute2/rt_tables
```

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `tag` | string | да | Уникальный идентификатор |
| `type` | string | да | `"table"` |
| `table` | integer | да | Номер существующей таблицы маршрутизации |

```json { filename="config.json" }
{
  "outbounds": [
    {
      "type": "table",
      "tag": "custom_table",
      "table": 200
    }
  ]
}
```

## `blackhole`

Отбрасывает подходящий трафик. Полезно для блокировки доступа к конкретным ресурсам.

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `tag` | string | да | Уникальный идентификатор |
| `type` | string | да | `"blackhole"` |

```json { filename="config.json" }
{
  "outbounds": [
    {
      "type": "blackhole",
      "tag": "block"
    }
  ]
}
```

## `ignore`

Оставляет трафик как есть: keen-pbr его не трогает, и он идёт по обычной маршрутизации роутера, как если бы keen-pbr не было.

Нужен для исключений. Правила проверяются сверху вниз, и срабатывает первое подходящее, поэтому правило с `ignore` ставят выше более общего правила. Например, весь список `streaming` идёт через VPN, кроме адресов из списка `streaming_direct` (`direct` — outbound типа `ignore` из примера ниже):

```json { filename="config.json" }
"rules": [
  { "list": ["streaming_direct"], "outbound": "direct" },
  { "list": ["streaming"], "outbound": "vpn" }
]
```

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `tag` | string | да | Уникальный идентификатор |
| `type` | string | да | `"ignore"` |

```json { filename="config.json" }
{
  "outbounds": [
    {
      "type": "ignore",
      "tag": "direct"
    }
  ]
}
```

## `urltest`

Используйте, когда у вас несколько каналов (например, два VPN и обычный интернет) и keen-pbr должен сам выбирать рабочий. keen-pbr периодически открывает `url` через каждый канал и измеряет время ответа.

Если ни один канал не работает, трафик этого outbound блокируется, а не уходит через обычный интернет мимо VPN.

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `tag` | string | да | Уникальный идентификатор |
| `type` | string | да | `"urltest"` |
| `url` | string | да | URL для проверки доступности и задержки |
| `interval_ms` | integer | нет (по умолчанию: `180000`) | Интервал между проверками в миллисекундах |
| `probe_timeout_ms` | integer | нет (по умолчанию: `5000`) | Таймаут одной проверки в миллисекундах |
| `tolerance_ms` | integer | нет (по умолчанию: `100`) | Не переключаться на другой канал, если он быстрее текущего меньше чем на столько миллисекунд |
| `strategy` | string | нет (по умолчанию: `"priority"`) | `"priority"` — весь трафик идёт через один, самый быстрый канал. `"balance"` — новые соединения распределяются между рабочими каналами первой рабочей группы пропорционально `weight` (недоступно на Keenetic) |
| `conntrack_on_switch` | string | нет (по умолчанию: `"preserve"`) | Что делать с открытыми соединениями при переходе на более быстрый канал: `"preserve"` — оставить на старом, `"delete"` — удалить их записи из {{< term "conntrack" >}}, чтобы они переподключились. См. [Резервный канал]({{< relref "/docs/configuration/advanced#резервный-канал-failover" >}}) |
| `outbound_groups` | array | да | Упорядоченный список групп каналов (см. ниже) |
| `retry` | object | нет | Повторные попытки проверки (см. ниже) |
| `circuit_breaker` | object | нет | Временное исключение нестабильного канала (см. ниже) |

```json { filename="config.json" }
{
  "outbounds": [
    {
      "type": "urltest",
      "tag": "auto_select",
      "url": "https://www.gstatic.com/generate_204",
      "interval_ms": 180000,
      "probe_timeout_ms": 5000,
      "tolerance_ms": 100,
      "outbound_groups": [
        { "members": [{ "outbound": "vpn1" }, { "outbound": "vpn2" }] },
        { "members": [{ "outbound": "wan" }] }
      ],
      "retry": {
        "attempts": 3,
        "interval_ms": 1000
      },
      "circuit_breaker": {
        "failure_threshold": 5,
        "success_threshold": 2,
        "timeout_ms": 30000,
        "half_open_max_requests": 1
      }
    }
  ]
}
```

### Группы outbound

`outbound_groups` — список групп по приоритету. keen-pbr использует первую группу, в которой есть хотя бы один рабочий канал. Если в группе не работает ни один канал, используется следующая.

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `members` | array of object | да | Каналы этой группы (см. ниже) |

Каждый канал в группе:

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `outbound` | string | да | Тег outbound (`interface`, `table` или `blackhole`) |
| `weight` | integer 1-100 | нет (по умолчанию: `1`) | Доля новых соединений при `strategy: "balance"`, при `priority` не используется. Каналы с весами 7 и 3 получат 70% и 30% новых соединений, пока оба работают |

```json { filename="config.json" }
"outbound_groups": [
  { "members": [ { "outbound": "wan1", "weight": 7 }, { "outbound": "wan2", "weight": 3 } ] },
  { "members": [ { "outbound": "backup" } ] }
]
```

{{< callout type="info" >}}
Старый формат групп (`outbounds: ["a", "b"]` и `weight` группы как её приоритет) тоже поддерживается. При первом запуске keen-pbr переписывает `config.json` в новый формат, а старый файл сохраняет рядом как `config.json.bak-pre-members`. Комментарии из старого файла в новый не переносятся. Смешивать старые и новые поля в одной группе нельзя.
{{< /callout >}}

### Балансировка (`strategy: "balance"`)

Канал выбирается для каждого нового соединения, а не для каждого запроса: всё соединение, включая HTTP/2 и {{< term "QUIC" >}}, идёт через один канал. `tolerance_ms` и `conntrack_on_switch` при балансировке не используются. Если канал перестал работать, записи {{< term "conntrack" >}} его соединений удаляются, а новые соединения распределяются между оставшимися каналами.

С nftables соединения распределяются точно по весам. С iptables канал выбирается случайно с нужной вероятностью, поэтому на малом числе соединений доли могут заметно отличаться от весов, а на большом выравниваются. Для iptables нужен модуль ядра `xt_statistic`; если его нет, keen-pbr сообщит об этом при применении конфигурации. С `--use-raw-prerouting` балансировка недоступна.

{{< callout type="info" >}}
Для балансировки между несколькими WAN нужны {{< term "NAT" >}} на каждом канале, нестрогий `rp_filter` и диапазон {{< term "fwmark" >}}, который не используют другие программы. Полная настройка для Debian/iptables описана на странице [Балансировка нагрузки между несколькими WAN]({{< relref "/docs/configuration/multi-wan" >}}).
{{< /callout >}}

### Повторные попытки (`retry`)

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `attempts` | integer | нет (по умолчанию: `3`) | Сколько раз повторить проверку, прежде чем считать канал нерабочим |
| `interval_ms` | integer | нет (по умолчанию: `1000`) | Пауза между попытками в миллисекундах |

### Исключение нестабильного канала (`circuit_breaker`)

Если канал несколько раз подряд не прошёл проверку, keen-pbr временно перестаёт его использовать. Так трафик не прыгает туда-обратно, когда канал то работает, то нет.

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `failure_threshold` | integer | нет (по умолчанию: `5`) | Сколько неудачных проверок подряд нужно, чтобы исключить канал |
| `timeout_ms` | integer | нет (по умолчанию: `30000`) | Через сколько миллисекунд снова попробовать исключённый канал |
| `success_threshold` | integer | нет (по умолчанию: `2`) | Сколько успешных проверок подряд нужно, чтобы вернуть канал |
| `half_open_max_requests` | integer | нет (по умолчанию: `1`) | Сколько проверок одновременно разрешено, пока исключённый канал проверяется повторно |

Исключённый канал отображается как **Недоступен** на странице **Outbounds** веб-интерфейса и как `unavailable` в `GET /api/runtime/outbounds`.

## `icmptest`

То же, что `urltest`, но каналы проверяются ping-ом ({{< term "ICMP" >}} Echo) вместо HTTP-запроса. Для каждого канала в группе задайте `target` — IP-адрес, который будет пинговаться через этот канал.

```json { filename="config.json" }
{
  "type": "icmptest",
  "tag": "auto_ping",
  "interval_ms": 60000,
  "count": 3,
  "max_failed": 0,
  "packet_interval_ms": 200,
  "probe_timeout_ms": 1000,
  "max_rtt_ms": 500,
  "tolerance_ms": 10,
  "outbound_groups": [
    {
      "members": [
        { "outbound": "vpn", "target": "1.1.1.1" },
        { "outbound": "wan", "target": "9.9.9.9", "weight": 3 }
      ]
    }
  ]
}
```

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `interval_ms` | integer | нет (по умолчанию: `60000`) | Интервал между проверками, от 1 секунды до 24 часов |
| `count` | integer | нет (по умолчанию: `3`) | Сколько ping-ов отправить в каждый канал за одну проверку, от 1 до 10 |
| `max_failed` | integer | нет (по умолчанию: `0`) | Сколько ping-ов из `count` может потеряться, чтобы канал всё ещё считался рабочим |
| `packet_interval_ms` | integer | нет (по умолчанию: `200`) | Пауза между ping-ами, от 100 до 1000 мс |
| `probe_timeout_ms` | integer | нет (по умолчанию: `1000`) | Сколько ждать ответа на один ping, от 100 до 5000 мс |
| `max_rtt_ms` | integer | нет (по умолчанию: `500`) | Ответ медленнее этого считается потерянным. Не больше `probe_timeout_ms` |
| `outbound_groups[].members[].target` | string | да | IPv4- или IPv6-адрес для ping через этот канал |

`tolerance_ms`, `strategy`, `conntrack_on_switch`, группы и веса работают так же, как у `urltest`.

Ping-и отправляются по очереди, поэтому проверка всех каналов занимает время. `interval_ms` должен быть больше этого времени хотя бы на 25%, иначе keen-pbr не примет конфигурацию и напишет минимально допустимое значение. Всего в группах может быть не больше 16 каналов.
