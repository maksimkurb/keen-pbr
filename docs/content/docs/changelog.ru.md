Что изменилось в каждой версии keen-pbr и что делать при обновлении.

## 3.4.0 {#v3-4-0}

### Что нового

- **Списки доменов работают без настройки резолвера.** keen-pbr сам читает DNS-ответы, проходящие через роутер, и имена сайтов в TLS-, HTTP- и QUIC-соединениях и заполняет наборы ваших списков. Уже первое соединение с сайтом идёт по нужному маршруту. Если в ядре чего-то не хватает, отключается только эта часть (DNS или соединения), а причина видна на странице состояния. См. [DNS]({{< relref "/docs/configuration/dns#dns-перехват" >}}).
- **dnsmasq стал необязательным.** Он нужен только для отдельных DNS-серверов для некоторых списков или для своих DNS-серверов по умолчанию. См. [Нужен ли dnsmasq?]({{< relref "/docs/configuration/dns#do-i-need-dnsmasq" >}}). keen-pbr сам выбирает экземпляр dnsmasq, показывает его состояние в веб-интерфейсе и чинит, если dnsmasq потерял конфиг. Новые команды: `keen-pbr dnsmasq detect` и `keen-pbr dnsmasq remove`.
- **Балансировка нагрузки между несколькими каналами** (`strategy: "balance"` в outbound `urltest`) с весом для каждого канала. Соединение остаётся на канале, через который началось. В сборке для Keenetic её нет. См. [Балансировка нагрузки между несколькими WAN]({{< relref "/docs/configuration/multi-wan" >}}).
- **Автоопределение шлюза** для interface-outbounds (`"gateway": "auto"`) и редактирование шлюза по умолчанию в веб-интерфейсе. См. [interface]({{< relref "/docs/configuration/outbounds#interface" >}}).
- **Весь интернет-трафик через резервный канал или балансировку**: новое условие правила `default_gateway` (только nftables). См. [Правила маршрутизации]({{< relref "/docs/configuration/route-rules" >}}).
- **Новый веб-интерфейс**: компактный обзор, живая таблица текущих запросов, журнал запросов с пояснениями к меткам и фильтрами, панель диагностики (проверки ядра идут первыми), новый редактор outbounds, обновление данных по живому потоку вместо опроса, удобнее на телефоне, страница настроек показывает значения по умолчанию.
- **Проверки состояния** предупреждают об отсутствии NAT или строгом `rp_filter` на балансируемых каналах, о чужих fwmark, пересекающихся с `fwmark.mask`, и об отсутствующих расширениях iptables. `keen-pbr status` показывает тот же список проблем, что и веб-интерфейс.
- **Endpoint для Prometheus** `GET /metrics`: задержка проб, выбранный канал, обновления списков, счётчики балансировки и перехвата. Есть дашборд Grafana и примеры алертов. См. [REST API]({{< relref "/docs/rest-api#get-metrics" >}}).
- **`keen-pbr test-routing`** принимает параметры пакета (протокол, порты, адреса, DSCP) и выполняется в демоне, так же как проверка маршрута в веб-интерфейсе.
- **Трафик самого роутера по умолчанию не трогается.** Правила маршрутизации действуют на устройства в сети. Чтобы включить и роутер, задайте `iproute.process_router_traffic: true`. См. [iproute]({{< relref "/docs/configuration/advanced#iproute" >}}).
- **В конфиге по умолчанию** есть правило, которое не пускает локальные сети в туннели.
- **Кнопка «Что нового?»** в веб-интерфейсе открывает эту страницу.
- Списки, которые не скачались при запуске, докачиваются в фоне.
- При удалении пакета убираются оставшиеся правила firewall и файлы dnsmasq.

### Исправления

- Группы `urltest` и `icmptest` принимали участников любого типа, хотя работают только `interface` и `table`. Теперь другие типы не проходят проверку конфига. Участник `blackhole` никогда не выбирался: keen-pbr пропускает его и пишет предупреждение в журнал. Для блокировки он не нужен: если ни один канал не работает, трафик блокируется сам.
- Автообновление списков останавливалось после первого изменения списка, влияющего на маршрутизацию. Теперь оно идёт по расписанию.
- Новые устройства не получали адрес по DHCP, если правило маршрутизации ловило весь UDP-трафик.
- При заданных `inbound_interfaces` трафик самого роутера обходил правила маршрутизации, даже если должен был под них попасть.
- Если один список упоминался в нескольких DNS-правилах, использовался сервер только из первого. Теперь dnsmasq получает серверы всех правил и переключается между ними.
- На Keenetic при обновлении аренды DHCP на WAN поток изменений маршрутов мог оставить маршрутизацию, собранную по наполовину обновлённой таблице.
- После пропадания питания файл кэша списка мог остаться пустым.
- `keen-pbr status` показывал ошибку у каждого правила `urltest` и `icmptest`.
- Веб-интерфейс терял `conntrack_on_switch`, `strict_enforcement_action` и таймаут пробы `urltest` при сохранении outbound.

### Обновление с 3.3.x {#upgrading-from-33x}

После обновления управление dnsmasq остаётся включённым, как в 3.3.x. Если dnsmasq вам не нужен, выключите **Управлять конфигурацией dnsmasq** в веб-интерфейсе (**Общее** > **Настройки** > **Управление локальным DNS-сервером**) и выполните шаги отката: [Keenetic]({{< relref "/docs/getting-started/installation/keenetic#dnsmasq-rollback" >}}), [OpenWrt]({{< relref "/docs/getting-started/installation/openwrt#dnsmasq-rollback" >}}), [Debian]({{< relref "/docs/getting-started/installation/debian#dnsmasq-rollback" >}}). Без него не работают DNS-правила и основные DNS-серверы.

Что проверить после обновления:

- **Keenetic: модули ядра.** Домены теперь определяются перехватом. Если компонент **Модули ядра подсистемы Netfilter** ещё не установлен, установите его. Затем откройте страницу состояния в веб-интерфейсе и запустите проверку DNS.
- **Keenetic: только iptables.** Сборка для Keenetic всегда работает через iptables. Конфиг с `daemon.firewall_backend: "nftables"` или `strategy: "balance"` там не пройдёт проверку.
- **Debian 11 (bullseye)** больше не поддерживается.
- **Изменились значения по умолчанию.**
  - `daemon.clear_dynamic_sets_on_apply` теперь `false`: адреса доменов сохраняются при применении конфига.
  - `ttl_ms` списка теперь нижняя граница; верхняя задаётся `intercept.max_ttl_ms`.
  - `iproute.process_router_traffic` равно `false`: правила маршрутизации действуют на устройства в сети, а не на трафик самого роутера.
  - `--log-target` для всех команд равен `both`. Пакетные файлы сервиса передают `--log-target syslog`.
- **Поля, которые больше не работают.** `dns.system_resolver`, `dns.dns_test_server` (используйте `intercept.dns.marker`) и `daemon.resolver_ready_timeout_seconds`; если они заданы, журнал предупредит. Старые поля `outbounds`, `candidates` и `weight` в `outbound_groups` заменены на `members`. Старые конфиги продолжают работать: keen-pbr один раз перепишет их и сохранит копию в `<config>.bak-pre-members`.
- **Новое поле `version`.** В нём версия keen-pbr, для которой записан конфиг. keen-pbr ставит его, когда вы сохраняете конфиг в веб-интерфейсе. Если правите файл вручную, оставьте его.
- **Домен для проверки DNS.** Для ручной проверки запускайте `nslookup check.keen-pbr.fyi` вместо `nslookup check.keen.pbr`. См. [Решение проблем]({{< relref "/docs/troubleshooting" >}}).

Если с keen-pbr работают ваши скрипты или другие программы:

- Команда `keen-pbr resolver-config-hash` ничего не делает и всегда завершается успешно.
- `keen-pbr generate-resolver-config` принимает `dnsmasq` вместо `dnsmasq-ipset` и `dnsmasq-nftset`.
- `keen-pbr status` завершается с кодом 1, если какая-то проверка не прошла или среди проблем есть ошибка.
- `GET /api/dns/test?show=all` (и `show=full`) работает только при включённой аутентификации API.
- Новые endpoint'ы: `GET /metrics`, `GET /api/health/issues`, `GET /api/config/defaults`. `GET /api/status/events` дополнительно присылает проблемы, состояние маршрутизации, состояние аутентификации и изменения конфига.
