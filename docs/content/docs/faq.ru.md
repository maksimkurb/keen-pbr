## Какой бэкенд firewall будет использоваться?

Выбор зависит от параметра `daemon.firewall_backend`. По умолчанию стоит `"auto"`: keen-pbr использует nftables, если в системе есть команда `nft`, а иначе iptables/ipset. На Keenetic всегда используется iptables/ipset.

## Как перезагрузить списки без перезапуска сервиса?

Выполните команду для вашей платформы:

{{< tabs >}}
{{< tab name="Keenetic / NetCraze" selected=true >}}
```bash {filename="bash"}
/opt/etc/init.d/S80keen-pbr reload
```
{{< /tab >}}
{{< tab name="OpenWrt" >}}
```bash {filename="bash"}
service keen-pbr reload
```
{{< /tab >}}
{{< tab name="Debian" >}}
```bash {filename="bash"}
systemctl reload keen-pbr
```
{{< /tab >}}
{{< /tabs >}}

Это полная перезагрузка: заново скачиваются все удалённые списки и повторно применяются правила межсетевого экрана и маршрутизации.

В сборке `keen-pbr-headless` эта команда не работает. Чтобы заново скачать списки и применить их, выполните `keen-pbr download --reload`.

{{% details title="Чем отличается «reapply-firewall»" closed="true" %}}
На Keenetic есть ещё команда `/opt/etc/init.d/S80keen-pbr reapply-firewall`. Она заново проверяет таблицы маршрутизации и сразу запускает проверки каналов `urltest` и `icmptest`, но списки не скачивает.
{{% /details %}}

## Что произойдёт, если URL удалённого списка недоступен при запуске?

keen-pbr использует кэшированную копию из `daemon.cache_dir`, если она доступна. Если кэша тоже нет, список только с `url` остаётся пустым, пока загрузка не удастся; keen-pbr продолжает попытки в фоне.

## Как urltest outbound выбирает лучший канал?

Каждые `interval_ms` keen-pbr отправляет HTTP-запрос на настроенный `url` через каждый канал и измеряет задержку ({{< term "RTT" >}}). При `strategy: "priority"` выбирается канал с наименьшей задержкой. Если новый лучший канал быстрее текущего меньше чем на `tolerance_ms`, переключения не происходит. Каналы проверяются по группам: следующая группа из `outbound_groups` используется, только если в предыдущей не работает ни один канал.

Если канал `failure_threshold` раз подряд не прошёл проверку, keen-pbr перестаёт его использовать на `timeout_ms`, а затем снова проверяет его несколько раз. Так трафик не прыгает между каналами, пока один из них работает нестабильно.

Outbound `icmptest` работает так же, но проверяет каждый канал ping-ом на адрес `target`, а не HTTP-запросом.

## Можно ли маршрутизировать DNS-запросы через VPN?

Да. Используйте поле `detour` в `dns.servers`, чтобы привязать DNS-запросы к этому серверу к конкретному outbound:

```json
{
  "servers": [
    {
      "tag": "vpn_dns",
      "address": "10.8.0.1",
      "detour": "vpn"
    }
  ]
}
```

## Какой формат файла списка?

Одна запись на строку. Поддерживаемые форматы:
- IPv4-адрес: `93.184.216.34`
- IPv6-адрес: `2606:2800:220:1:248:1893:25c8:1946`
- {{< term "CIDR" >}}: `10.0.0.0/8`
- Домен: `example.com` (автоматически включает все поддомены)
  - записи вида `*.example.com` работают так же, как `example.com`
- Строки, начинающиеся с `#`, — комментарии, их пропускают
- Пустые строки пропускаются

## Как проверить, что маршрутизация правильно применена?

Выполните:

```bash {filename="bash"}
keen-pbr status
```

keen-pbr сравнит правила firewall, таблицы маршрутизации и записи `ip rule` в ядре с тем, что он ожидает, и отметит каждый пункт как `OK`, `MISSING`, `MISMATCH` или `ERROR`. Та же проверка есть в веб-интерфейсе: панель **Диагностика** на странице **Общее** > **Обзор системы**. Чтобы проверить конкретный сайт, нажмите **Куда пойдёт трафик?** на той же странице или выполните `keen-pbr test-routing <домен-или-ip>`.

## Почему проверка с самого роутера не идёт через VPN? {#router-own-traffic}

Параметр **Обрабатывать собственный трафик роутера** (виден в режиме настроек **Продвинутый**) (**Общее** > **Настройки** > **Общие**) по умолчанию выключен: правила действуют на трафик устройств из локальной сети, а не на команды вроде `curl` в SSH-консоли роутера. Проверяйте маршрутизацию с устройства в сети. Также убедитесь, что устройство подключено через интерфейс из списка **Обрабатываемые (входящие) интерфейсы**, если этот список не пуст.

## Можно ли объединить несколько источников в одном списке?

Да. Можно объединять `url`, `domains`, `ip_cidrs` и `file` в одной записи списка — данные объединятся:

```json
{
  "lists": {
    "combined": {
      "url": "https://example.com/remote.txt",
      "domains": ["extra.example.com"],
      "ip_cidrs": ["192.168.100.0/24"],
      "file": "./local.txt"
    }
  }
}
```

{{< callout type="warning" >}}
Веб-интерфейс умеет объединять только `ip_cidrs` и `domains`. Не добавляйте к ним `url` или `file`: веб-интерфейс такое сочетание не поддерживает, а в будущих версиях его могут запретить.
{{< /callout >}}
